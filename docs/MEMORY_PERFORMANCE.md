# Память: повторное использование проверенного и раздельные измерения

6 октября 2026. Исходная ревизия для сравнения:
`11eb53a0bd2ac466a54f10515afa9059fedd733f`. Измеренная ревизия:
`a951dd9d732f9784af116a757385f37f8f1955fc` (пакет доделки ревью PR108, чистое
дерево). Замеры ручные: ни одна цифра отсюда не является порогом приёмки, и ни
один pytest-файл не измеряет время.

## Что изменено (§8.3)

- **Снимок состояния и хвост журнала.** Суд — единственный писатель — каждые
  восемь отчётов записывает `MEMORY_STATE`: версию проекции
  (`synapse.memory.state-projection/v1`), срез (решение и квитанцию его
  отчёта) и дайджест состояния. Владелец берёт последний снимок, совпавший по
  версии, срезу и дайджесту, и сворачивает только отчёты после него; иначе
  сворачивает весь журнал. Повреждённый снимок, снимок другой версии и срез,
  которого цепочка не содержит, не используются никогда.
- **Отчёты из проверенного скана.** Отчёт решения читается из событий журнала,
  уже проверенных при построении цепочки, по квитанции, которую назвало
  решение; решение с чужой квитанцией отвергается.
- **Новейшая граница снимка с головы цепочки.** Сессия ищет границу от
  последнего отчёта к первому; состояние для перестройки отстающей границы
  нужно только ей.
- **Проверенные байты журнала не проверяются повторно.** Канонический разбор
  события запоминается по транзакции и SHA-256 её байтов; хэш и маркер
  проверяются при каждом чтении, копия возвращается глубокой.
- **Точное смысловое ранжирование.** Каждый записанный вектор сравнивается
  (приближённого индекса нет, полезный кандидат не теряется), норма запроса
  считается один раз, оценки — те же числа с плавающей точкой, что и при
  попарном счёте, равные оценки упорядочены по идентичности.

Повторные проверки подтверждённых неизменных оснований экономит переиспользование
гипотез; это считают приёмочные файлы (экзамен A проверяет, экзамен B
переиспользует), здесь оно не хронометрируется.

## Как измерено

`scripts/benchmark_memory_reuse.py` в каждой из двух ревизий строит одну и ту же
память — 40 сессий подсчёта запасов, каждая отдельным долговечным запуском
`python -m synapse run` со своей консолидацией, — и затем измеряет медиану
пяти повторов:

1. восстановление того же состояния из журнала (`MemoryOwner.state`);
2. повторную проверку неизменного префикса журнала (`MemoryOwner.applied`) и
   поиск новейшей границы снимка, которую закрепляет сессия, с числом чтений
   событий журнала;
3. смысловое ранжирование по 5000 записанным векторам размерности 384 (бюджет
   25); выдача обеих ревизий обязана совпасть байт в байт;
4. ещё одну сессию целиком.

Python 3.11.15, Linux x86_64, четыре ядра. Во время замера на другом ядре шёл
один приёмочный файл; обе ревизии мерились подряд в тех же условиях.

## MemoryArena: групповое планирование без модели (15 октября 2026)

MemoryArena (He et al., arXiv 2602.16313) планирует поездку группы по одному
путешественнику; условия следующих ссылаются на выбор предыдущих («рейтинг в
пределах 0.3 от жилья Kelly на второй день»), поэтому план, сделанный для Kelly,
должен вернуться из памяти. Домен Group Travel Planner оценивает планы
сравнением строк с эталоном (PS, SPS, SR), без модели-судьи. Планирует модель,
а её здесь нет, поэтому измерено то, что модели не требует. Выпуск данных
закреплён: `ZexueHe/memoryarena`, ревизия `da1a37c8…`, файл
`group_travel_planner/data.jsonl`, SHA-256 `2f955d44…`; 270 групп, 1869
путешественников. Из них 1562 ссылаются в условиях хотя бы на одного
предыдущего. Строка спутников («I'm going on this trip with …») называет
всех, остаётся в запросе и зависимостью не считается.

`scripts/memoryarena_memory_server.py` отвечает на API памяти бенчмарка
(`initialize`, `add`, `wrap_user_prompt`) лексическим каналом
`palace-lexical/v2` через `PreparedKnowledgeIndex.rank`. Куски режутся на те же
2048 токенов, что и в `RAGMemorySystem` бенчмарка, поэтому сравнение с его BM25
меняет только ранжирование. С `--memoryarena` тот же сервер отдаёт BM25 и long
context кодом самого бенчмарка.

**Батарея без модели** (`scripts/benchmark_memoryarena_travel.py`). Перед
каждым путешественником память содержит запись базового человека и по записи
на каждого предыдущего в формате прогона, с эталонным планом в `final_plan` и
пустым черновиком. Запрос — вопрос путешественника. Мера — попали ли в контекст
все записи, на которые ссылаются условия (`recall_all`), и их доля.

| Система | recall_all | доля зависимостей | токенов контекста |
|---|---:|---:|---:|
| Synapse lexical, top 3 | 0.718 | 0.868 | 2287 |
| BM25 MemoryArena, top 3 | 0.589 | 0.807 | 2180 |
| Synapse lexical, top 5 | 0.962 | 0.984 | 3155 |
| BM25 MemoryArena, top 5 | 0.917 | 0.966 | 3106 |
| long context | 1.000 | 1.000 | 3542 |

По числу записей в памяти top 3: Synapse 0.895, 0.644, 0.411, 0.366, 0.309 при
4–8 записях, BM25 0.444, 0.367, 0.306, 0.344, 0.474. При двух-трёх записях
обе выдачи содержат всю память.

**Сухой прогон конвейера бенчмарка.** `run_travel.py` MemoryArena запущен без
изменений на всех 270 группах: сервер среды бенчмарка, сервер памяти выше и
`scripts/memoryarena_oracle_endpoint.py` вместо модели. Оракул сначала
вызывает настоящие инструменты среды (рестораны, жильё и достопримечательности
городов маршрута), затем отвечает эталонным планом. PS, SPS и SR — 100% для
всех четырёх систем: разбор, сборка и оценка связаны правильно, качество
планирования этим не измеряется. Записи памяти здесь несут черновик с
результатами инструментов, в среднем 23 962 символа на запись. Мера: дошли ли
планы упомянутых путешественников до запроса агента.

| Система | recall_all | доля зависимостей | символов контекста |
|---|---:|---:|---:|
| Synapse lexical, top 3 | 0.121 | 0.153 | 25 528 |
| BM25 MemoryArena, top 3 | 0.132 | 0.170 | 24 863 |
| Synapse lexical, top 5 | 0.271 | 0.335 | 39 664 |
| long context | 1.000 | 1.000 | 87 996 |

С четвёртого путешественника выборка кусков (и Synapse, и BM25) не приносит
нужных планов: верх занимают таблицы ресторанов и жилья из черновиков, которые
совпадают со словами вопроса лучше, чем план. Long context приносит всё, но к
восьмому путешественнику это 173 576 символов. Батарея с эталонными планами без
черновиков показывает обратное: когда в памяти итог эпизода, а не его сырой
след, тот же канал находит зависимости в 72–96% случаев. Решает то, что память
хранит, а не ранжировщик.

Полный отчёт с разбивкой по числу записей и по путешественнику —
`reports/memoryarena_travel_v1.json`.

## Порядок утверждений (повторное ревью 556624d)

Порядок утверждений памяти (`knowledge.stated`) хранит одну запись на чтение
источника. `scripts/benchmark_knowledge_order.py` складывает чтения одного
источника через стадии знания и гипотез суда, по сто чтений в окне, и
применяет каждое окно так же, как его отчёт: проекция присоединяет то, что
отчёт добавляет к порядку. Для порядков из 100, 1000 и 5000 чтений, без
гипотез и со 100 гипотезами, опирающимися на источник, измерено ещё одно окно,
читающее источник: медиана пяти повторов, байты порядка в состоянии и байты,
которые добавляет отчёт окна.

## Ограничения

- Точность ответов LongMemEval (QA) не измерена: читающая модель Synapse
  работает через брокер, а ключа провайдера в этой среде нет. Внешний судья
  ответов, если его подключить, полномочий в системе не получает.
- Смысловой канал на LongMemEval не измерен: внешней модели эмбеддингов здесь
  нет; сценарный эмбеддер приёмочных файлов доказывает связность, а не качество.
- MemoryArena: качество планов (PS, SPS, SR планирующей модели) не измерено:
  ключа провайдера здесь нет. Измерены поиск без модели и связность конвейера
  бенчмарка; остальные три домена (покупки, поиск, формальные рассуждения) не
  запускались.
- Память замера синтетическая и небольшая (40 сессий); A/B/C — три задачи,
  это парное сравнение, а не статистическое утверждение.
- События `MEMORY_STATE` и `MEMORY_TRIAL` входят в бюджет журнала проекта
  (4096 событий): снимок добавляет одно событие на восемь отчётов.
- Один прогон на одной машине; цифры времени — наблюдение, а не гарантия.

Конфиг сухого прогона — конфиг travel бенчмарка с `memory_system_name`
(`synapse-lexical`, `synapse-lexical-5`, `bm25`, `long_context`),
`server_url` `http://127.0.0.1:8010`, `env_server_url`

**Живой прогон** идёт в GitHub Actions (`.github/workflows/memoryarena-travel.yml`)
с секретом репозитория `GEMINI_API_KEY`. Пуши его не запускают: прогон
начинается, когда сопровождающий ставит на PR этого репозитория метку
`memoryarena:smoke` (группа 8, пять путешественников, память Synapse) или
`memoryarena:pilot` (первые двадцать групп; режим бенчмарка без памяти, где
прежние планы стоят в запросе, long context, BM25 и Synapse). Задания идут по
одному, а вызовы разнесены на 4,5 секунды: ключ репозитория работает на
бесплатном уровне, 15 запросов в минуту на модель (так называет квоту ответ 429
провайдера). `scripts/memoryarena_live_run.py prepare` закрепляет коммит
MemoryArena `6cd9de14…`, таблицу перелётов (SHA-256 `8dafdb0e…`) и ревизию
данных и отказывает, если ревизия на Hugging Face сдвинулась.
`scripts/memoryarena_live_run.py run` поднимает оба сервера, пишет конфиг и
сводку `summary.json`: PS, SPS, SR бенчмарка, токены провайдера по вызовам,
шаги агента и долю вопросов, в которые память донесла планы упомянутых
путешественников. Итог всех заданий — таблица в сводке прогона и артефакт
`memoryarena-report`.

Клиент Gemini самого MemoryArena (`GeminiClient`) пересобирает разговор из
сообщений агента и выбрасывает ходы модели с вызовами функций. Результаты
инструментов приходят модели без вызовов, на которые они отвечают, а подписи
мыслей, которых требуют модели Gemini 3, теряются. Транспорт `gemini-rest` в
`scripts/memoryarena_run_travel.py` возвращает каждый ход модели в том виде, в
каком его выдал API, и отвечает на вызовы хода одним ходом ответов функций.
Агент, его промпты и инструменты, память и оценка остаются кодом MemoryArena.
Оракул сухого прогона отвечает и по REST-протоколу Gemini и отказывает с
HTTP 400 в историях, которые отклоняет API: ответ функций не сразу после хода с
тем же числом вызовов или ход вызовов без выданной подписи.

**Первый живой прогон** (15 октября, `memoryarena:smoke`, run `38751119297`,
`gemini-3.1-flash-lite`, группа 8, пять путешественников, память Synapse).
Через `gemini-rest`: PS 0/5, SPS 11,19%, SR 0/1; 13 вызовов, 107 435 входных

## Группировка версий за запрос — 11 октября 2026

Первый патч поверх `fc5509e0f1c29fecece4427b6f95c6dbe053e501` устраняет
повторные обходы в `knowledge.search`. После ранжирования для выбранных
`slot` (предмет, свойство, условия) все версии собираются за один проход.
Порядок выбранных групп, порядок версий внутри них, временное разрешение,
конфликты, происхождение, бюджеты и полная выдача сохраняются. Группировка
выполняется после embedding, как прежний сбор версий. Это локальное
представление одного запроса; постоянного индекса, кеша, нового формата
хранения или дополнительного доступа worker нет.

При `N` версиях и `K` выбранных группах сбор членов групп требует одного
обхода `N` вместо `K × N`. Это оценка заменённого участка, не всего поиска:
ранжирование и временное разрешение выполняют прежнюю работу. Группировка
держит не более `N` ссылок на записи выбранных групп и `K` списков; записи
и векторы не копируются. Ссылки освобождаются после запроса. По сравнению
с прежней обработкой одной группы за раз одновременно удерживается больше
ссылок, но постоянная память системы не увеличивается.

Старое тело `search` сохранено только в
`acceptance/memory/_search_reference.py`. Приёмка сравнивает канонические

и бюджетами. Дополнительно проверены явные ожидаемые значения. Неизменённые
ranker и timeline общие с продуктом: этот оракул предназначен для приёмки
замены обходов, не для будущей замены ранжирования или временных правил.

Раньше `MemoryOwner` запрашивал копию всего inventory ради одного вида
событий: привязки конфигурации, открытых сессий, проходов retention,
испытаний или границ снимка. Остальные события, включая крупные

чтение. Внутри уже открытой сессии используется прежний проверенный inventory;

закреплённого снимка. Postings содержат идентификаторы записей; группы
содержат ссылки на исходные версии. Полные записи, происхождение, векторы,
история статусов и противоречия остаются у прежних владельцев. Старый
продуктовый обход для лексического ранжирования удалён; его независимая
копия существует только в приёмочном стенде.

Подготовка ленивая. Первый непустой лексический запрос строит postings;
semantic-only запросы этого не делают. Группы строятся при первом достигнутом
слоте после вызова embed. Прямой вызов `knowledge.search.search` без сессии
создаёт свежую проекцию для каждого обращения: изменения источника между
такими вызовами и добавление соседней версии во время embed сохраняют
прежнюю семантику. Переданная проекция должна принадлежать тому же mapping;
проверка идентичности запрещает смешение источников, но не является
проверкой свежести изменяемых данных.

Сессия сохраняет свой исходный проверенный срез после консолидации. Новая
сессия, восстановление и replay получают собственную проекцию своего среза.
Общего кеша между сессиями, TTL, постоянного индекса, SQLite и нового
формата хранения нет. Подготовленная проекция не записывается в историю
или checkpoint. Новая граница требует полного ленивого построения;
инкрементального обновления этот патч не реализует.

При каждом запросе заново применяются `known_as_of`, `valid_at`, правила
разрешения слота, ограничения embedder, прежний float64 cosine, округление,
RRF, tie-break по идентификатору и бюджеты. Лексическая формула осталась
у владельца palace scorer: округлённая до шести знаков доля различных
совпавших токенов запроса. Подготовленные структуры не содержат готовых
ответов, решений admission или разрешений на действие. Поле результата
`cost.index_bytes` сохраняет прежнее значение для векторов; дополнительная
RAM проекций измеряется отдельно, без изменения формата истории.

Проверка владения выявила существовавший alias: изменение вложенного
`entity` в возвращённом DSL-решении `admit` могло изменить закреплённое
знание или записанное решение. Это нарушило бы корректность любой
подготовленной проекции. Теперь поисковый кандидат является отделённым
значением, а `Interpreter.evaluate_admission` возвращает отделённую копию
решения. Два приёмочных случая через настоящий CLI изменяют результат
допуска и результат отказа, затем повторяют поиск и допуск. Оба падают
на исходной версии из-за изменившегося содержимого и проходят после
исправления с сохранением истории, состояния владельца и replay.

Профиль версии после выборочного копирования inventory показал в шести
вызовах поиска 1.208 с, включая потомков: группировка — 0.809 с,
лексическое ранжирование — 0.334 с. Эти вложенные времена не складываются.
Весь инструментированный стенд с проверками и replay занял 249.106 с;
он служит выбору участка, не измерению ускорения. Поэтому проекция
подготавливает обе повторяемые структуры. Сценарий эвакуации с одним
поиском на сессию остаётся функциональной проверкой первого обращения.

Для измерения повторных обращений добавлен собственный исторический
разбор того же инцидента. Корпус получен настоящими durable-запусками:
24 узла, 6 стоек, 1536 шардов с тремя репликами, отказ узла после 24
перемещений, исправление свободной ёмкости, отказ устаревшему плану,
перепланирование, 962 выполненных перемещения, 3168 версий в четырёх
окнах суда. Новый разбор делает 64 различных полных запроса: 16 текстов
на четырёх временных срезах, включая время до наблюдения и ситуацию,
когда исправление ещё не было известно памяти.

Каждый полный поисковый результат сравнивается с замороженным прежним
алгоритмом. Отдельный oracle восстанавливает состояние кластера по
исходной модели и первым 24 перемещениям, проверяет значения всех
возвращённых кандидатов, отказ узла 12 и свободную ёмкость узла 5.
Разбор проходит публичный durable runtime и пятое окно суда; знание
остаётся неизменным, инструмент не вызывается. `COMPLETED` здесь означает
завершённое выполнение программы; признание задачи решённой или статус
Gold `FULL` этим сценарием не заявляются.

Локально прошли 258 целевых проверок: 34 новых случая и 224 существующих.
Тяжёлые файлы prepared-search-scale, prepared-search-custody и storage-audit
получили отдельные задания CI; полный набор репозитория не запускался.
В существующей проверке направления зависимостей добавлено ребро от
проекции к владельцу palace scorer; после этого её два случая прошли.
Pre-commit gate также прошёл: 45 примеров разбираются, покрытие CVM
0.935620 при пороге 0.9332.

Ресурсные проверки вызывают прежний `MemorySession.search_knowledge`:
старая версия проваливает ограничения на повторную токенизацию и повторную
канонизацию слотов, сохраняя правильную выдачу. Корпус из 2560 версий
проверяется также по полным результатам lexical, semantic и hybrid,
временным срезам и противоречиям. Порогов по времени, RSS, длине файлов
или числу функций приёмка не вводит.

База измерений — `f2bf791` с уже применённым предыдущим патчем выборочного
inventory. Таким образом, выигрыш подготовленного поиска измеряется
отдельно от двух предыдущих оптимизаций. Для трёх пар порядок процессов
чередуется: исходная → патч, патч → исходная, исходная → патч. Каждый
durable-разбор получает новую копию одного сохранённого корпуса; исходные
абсолютные ссылки на артефакты сохраняются. Проверяются SHA-256 всех
продуктовых Python-файлов и используемого стенда до и после каждого
процесса, а драйверы записывают фактические пути импортированных модулей.
Окружение Python 3.12.14 и зависимости зафиксированы.

Сквозной интервал включает выполнение программы и консолидацию. Создание
исходного корпуса, его копирование, oracle, сравнение результатов и replay
измеряются вне этого интервала. Отдельный causal-драйвер открывает через
настоящий `MemoryFactory` удерживаемые границы окон 2 и 4: 1584 и 3168
версий соответственно. Время открытия владельца, открытия сессии, первого

очищается, поэтому это не измерение холодного дискового чтения.

## Раздельный профиль открытия памяти — 11 октября 2026

После подготовки поиска закрыта общая ссылка входного `claim` с историей
допуска: существующий нормализатор сохраняет собственную копию проверяемого
утверждения. Приёмка, точный небольшой product diff и хеши предыдущего
состояния записаны в `reports/memory_admission_input_custody_v1.json`.
Дальнейшая работа этого этапа — исследование стоимости чтения памяти;
нового формата хранения или оптимизации чтений здесь ещё нет.

Уточнение предыдущего измерения: `owner_open` включал конструктор владельца
и `bound_configuration`, а `session_open` использовал read-only exam B.
Их сумма около 5.6 с не является временем каждого обычного открытия сессии.
Эти пути теперь рассматриваются отдельно:

| Путь | Граница проверенного чтения |
| --- | --- |
| Обычный `open_session` | Полный скан при входе в owner session, дальнейшие обращения под её guard |
| Exam B | Несколько чтений без guard при проверке привязки, policy и закреплённой границы |
| Повторное открытие записанного запуска | Обычная owner session с восстановлением исторического pin |
| Replay внутри суда | Суд удерживает owner session, но чтение pin обращается к владельцу без guard |
| `owner.state` | Проверенная цепочка отчётов; при подходящем `MEMORY_STATE` — проверка снимка с последующим хвостом |

Стенд `acceptance/memory/memory_open_profile` наблюдает реальные функции
через Python 3.12 `sys.monitoring` и отдельные `cProfile`. Продуктовые
методы не заменяются. Конструктор владельца, чтение конфигурации, чтение
границ, восстановление состояния, вход под guard, exam, повторное открытие
записанного запуска и обычный durable-путь имеют отдельные интервалы.
Повторное открытие API не выдаётся за полный CLI resume.

Время `cProfile` служит диагностике, а не сравнению скорости патчей.
Категории собственного времени функций не пересекаются; вложенные
`cumulative`-времена нельзя складывать. Audit hook считает открытия файлов
для чтения. Размер уникальных файлов после запуска учитывается отдельно:
он не означает число прочитанных байт или физические обращения к диску.
`fresh-reader` означает новый объект читателя, `reused-reader` — повторное
обращение того же читателя. Кеш ОС не очищается.

Все операции записи выполняются на копиях настоящего корпуса инцидента.
Помимо четырёх исходных окон рассматривается пятое окно исторического
расследования. В них ещё нет `MEMORY_STATE`; отдельная копия доводится
настоящими durable-запусками до восьмого окна, где штатно публикуется
материализованное состояние. Подготовка этого корпуса не включена во
времена последующих чтений.

Истории окон 4 и 8 различаются; сравнение их времени не измеряет эффект
введения снимка. RSS и холодное чтение диска здесь не измерялись.

Следующий узкий патч — устранить повторное `canonical(event) != raw` в
`ProjectMemoryStore._read`. Вызываемый перед ним строгий decoder уже
канонизирует только что разобранное дерево и сравнивает его с исходными
байтами. Оба пути используют одинаковые profile/codec; между проверками
дерево не передаётся вызывающему. Это кандидат для первого чтения:
повторное чтение тем же объектом уже обходит эту ветку.

В следующей приёмке должны сохраниться отказы на неканонических данных
с **корректным физическим commit marker**, иначе проверялся бы лишь хеш
транзакции. Нужны также прежние типы ошибок, чтение старых записей,
независимость возвращённых данных и парное измерение настоящего запуска
с консолидацией без профайлера. Проверки размера, структуры записи,
полученного receipt, commit marker и физических байтов остаются на месте.
В текущем этапе этот код ещё не изменён.

Устранение второго обхода внутри общего decoder, повторное использование
проверенного inventory под guard и общее хранение снимков — самостоятельные
следующие изменения. Для повторного использования нужны явные границы
владения, актуальности и публикации; кеш по имени или времени изменения
файла не заменяет физическую проверку. Gold `REQUESTED`/`FRAME_COMPLETED`
и разрешение ссылок worker frame этим профилем не покрыты.

Воспроизведение профиля требует Python 3.12+ только для приёмочного
`sys.monitoring`; минимальная версия Python продукта не меняется. Исходный
корпус готовится сценарием `storage_evacuation` из предыдущего раздела,

Дополнительные проверки последствий:

- Replay-data живой сессии с нулём ссылок позже стало основанием девяти
  случаев. Удалять по отсутствию текущих ссылок нельзя. Для четырёх завершённых
  plan-only сессий парный опыт снял 1 312 144 байта без изменения проверенных
  случаев, reassess, retention и restore. Общий GC этим не обоснован.
- Настоящая задача со 121 элементом и 172 условиями публикуется: expanded
  frame 16 547 484 байта, компактное событие 644 906 байт, worker envelope
  128 668 байт до добавления профиля доставки. На 173 условиях expanded budget
  отказывает. Прежние данные читаются, следующая маленькая задача проходит.
  Поэтому текущий лимит frame нельзя приравнивать к лимиту prompt.
- Компонентный registry с 65 536 историческими каталогами отказывает даже
  при одном активном owner: полный `subsystems` даёт 8 849 258 байт. Это
  физически сохранённый синтетический ввод формы суда, не 2048 исполненных
  Gold-задач. Положительные контроли сжатия registry сохраняют точный frame,
  выдачу worker и восстановимость полных оснований.
- Удаление заведомо неиспользуемого входа и комментария сохранило все 32
  traces и 310 событий выбранного сценария; экономия 32 944 байта, 1,46%
  всего состояния. Удаление используемого входа или программы нарушает replay.
  Обрезание ответов инструментов меняет свидетельства: 0/32 traces;
  обязательный retention gate сохраняет raw. Миграция исторических refs
  и универсальный анализ зависимостей этим экспериментом не реализованы.
- Один legacy-корпус воспроизведён 32/32 на четырёх конкретных реализациях.
  Исторический `1b58d18` с той же executor-строкой даёт 0/16 в первой сессии;
  его собственный gate обнаруживает расхождение. Новый reader читает старый
  формат; отказы старых readers на новом event-tree отмечены отдельно.
  Полная копия исходников Synapse в памяти для этих replay не требовалась.

универсальная минимальность сохраняемых данных и совместимость с произвольным
runtime не установлены. Исправление доставки описано отдельно в
