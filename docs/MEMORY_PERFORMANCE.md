# Память: повторное использование проверенного и раздельные измерения

6 октября 2026. Исходная ревизия для сравнения:
`11eb53a0bd2ac466a54f10515afa9059fedd733f`. Измеренная ревизия:
`a951dd9d732f9784af116a757385f37f8f1955fc` (пакет доделки ревью PR108, чистое
дерево). Замеры ручные: ни одна цифра отсюда не является порогом приёмки, и ни
один pytest-файл не измеряет время.

## Что изменено (§8.3)

- **Снимок состояния и хвост журнала.** Суд — единственный писатель — каждые
  восемь отчётов записывает `MEMORY_STATE`: версию проекции
  (`synapse.memory.state-projection/v1`), срез (решение и квитанцию его
  отчёта) и дайджест состояния. Владелец берёт последний снимок, совпавший по
  версии, срезу и дайджесту, и сворачивает только отчёты после него; иначе
  сворачивает весь журнал. Повреждённый снимок, снимок другой версии и срез,
  которого цепочка не содержит, не используются никогда.
- **Отчёты из проверенного скана.** Отчёт решения читается из событий журнала,
  уже проверенных при построении цепочки, по квитанции, которую назвало
  решение; решение с чужой квитанцией отвергается.
- **Новейшая граница снимка с головы цепочки.** Сессия ищет границу от
  последнего отчёта к первому; состояние для перестройки отстающей границы
  нужно только ей.
- **Проверенные байты журнала не проверяются повторно.** Канонический разбор
  события запоминается по транзакции и SHA-256 её байтов; хэш и маркер
  проверяются при каждом чтении, копия возвращается глубокой.
- **Точное смысловое ранжирование.** Каждый записанный вектор сравнивается
  (приближённого индекса нет, полезный кандидат не теряется), норма запроса
  считается один раз, оценки — те же числа с плавающей точкой, что и при
  попарном счёте, равные оценки упорядочены по идентичности.

Повторные проверки подтверждённых неизменных оснований экономит переиспользование
гипотез; это считают приёмочные файлы (экзамен A проверяет, экзамен B
переиспользует), здесь оно не хронометрируется.

## Как измерено

`scripts/benchmark_memory_reuse.py` в каждой из двух ревизий строит одну и ту же
память — 40 сессий подсчёта запасов, каждая отдельным долговечным запуском
`python -m synapse run` со своей консолидацией, — и затем измеряет медиану
пяти повторов:

1. восстановление того же состояния из журнала (`MemoryOwner.state`);
2. повторную проверку неизменного префикса журнала (`MemoryOwner.applied`) и
   поиск новейшей границы снимка, которую закрепляет сессия, с числом чтений
   событий журнала;
3. смысловое ранжирование по 5000 записанным векторам размерности 384 (бюджет
   25); выдача обеих ревизий обязана совпасть байт в байт;
4. ещё одну сессию целиком.

Python 3.11.15, Linux x86_64, четыре ядра. Во время замера на другом ядре шёл
один приёмочный файл; обе ревизии мерились подряд в тех же условиях.

## Ограничения

- Точность ответов LongMemEval (QA) не измерена: читающая модель Synapse
  работает через брокер, а ключа провайдера в этой среде нет. Внешний судья
  ответов, если его подключить, полномочий в системе не получает.
- Смысловой канал на LongMemEval не измерен: внешней модели эмбеддингов здесь
  нет; сценарный эмбеддер приёмочных файлов доказывает связность, а не качество.
- MemoryArena не запускалась.
- Память замера синтетическая и небольшая (40 сессий); A/B/C — три задачи,
  это парное сравнение, а не статистическое утверждение.
- События `MEMORY_STATE` и `MEMORY_TRIAL` входят в бюджет журнала проекта
  (4096 событий): снимок добавляет одно событие на восемь отчётов.
- Один прогон на одной машине; цифры времени — наблюдение, а не гарантия.

## Группировка версий за запрос — 11 октября 2026

Первый патч поверх `fc5509e0f1c29fecece4427b6f95c6dbe053e501` устраняет
повторные обходы в `knowledge.search`. После ранжирования для выбранных
`slot` (предмет, свойство, условия) все версии собираются за один проход.
Порядок выбранных групп, порядок версий внутри них, временное разрешение,
конфликты, происхождение, бюджеты и полная выдача сохраняются. Группировка
выполняется после embedding, как прежний сбор версий. Это локальное
представление одного запроса; постоянного индекса, кеша, нового формата
хранения или дополнительного доступа worker нет.

При `N` версиях и `K` выбранных группах сбор членов групп требует одного
обхода `N` вместо `K × N`. Это оценка заменённого участка, не всего поиска:
ранжирование и временное разрешение выполняют прежнюю работу. Группировка
держит не более `N` ссылок на записи выбранных групп и `K` списков; записи
и векторы не копируются. Ссылки освобождаются после запроса. По сравнению
с прежней обработкой одной группы за раз одновременно удерживается больше
ссылок, но постоянная память системы не увеличивается.

Старое тело `search` сохранено только в
`acceptance/memory/_search_reference.py`. Приёмка сравнивает канонические
байты полного результата во всех каналах, на двух временах, с исправлениями,
возвращением знания, забыванием, противоречиями, разными embedding-контрактами
и бюджетами. Дополнительно проверены явные ожидаемые значения. Неизменённые
ranker и timeline общие с продуктом: этот оракул предназначен для приёмки
замены обходов, не для будущей замены ранжирования или временных правил.
Большой корпус содержит 2 560 версий; 100 ранжированных записей раскрывают
200 кандидатов с независимыми противоречиями. Отдельные случаи проверяют
линейное число посещений корпуса, без порогов времени.

Сквозной стенд `acceptance/memory/storage_evacuation/` выполняет собственную
задачу эвакуации 1 536 шардов по три реплики на 24 узлах в шести стойках.
После первого пакета из 24 перемещений отказывает узел 12, а свободная
ёмкость узла 5 сокращается до восьми единиц. Устаревший пакет получает
`STALE_TOPOLOGY` без эффекта. Повторное обследование сохраняет исправления,
планировщик читает их из памяти, затем строит новый план. Модель ресурса
независимо от DSL-планировщика проверяет каждое перемещение: минимум две
живые копии, разные стойки, соблюдение вместимости. В конце остаются три
живые копии каждого шарда, эвакуируемые и отказавшие узлы пусты.

Четыре фазы проходят публичный `execute_durable_run`, шлюз инструментов,
настоящую консолидацию и журнал памяти. Это локальная модель ресурса;
внешний кластер, сеть MCP и языковая модель не участвуют. Итог: 962
перемещения, 48 вызовов transport, один отказ без эффекта, два плана,
3 168 сохранённых версий знания и четыре окна суда.

Replay проверяет записанный префикс каждой фазы до `session_consolidated`:
он не проводит консолидацию повторно. Проверяются `replay_verified`,
отсутствие новых вызовов transport и неизменность модели ресурса. Runtime
сопоставляет запрос и идентичности кандидатов, затем возвращает записанную
выдачу; полное равенство результатов нового поиска отдельно доказывают
сравнения с прежним `search`. Новым runtime также воспроизводится запись
исходной ревизии.

Измерены три пары в порядке baseline/patch, patch/baseline, baseline/patch,
каждый запуск в новом процессе и новом каталоге. Использован один неизменный
Python 3.12.14 на Linux x86_64; другие тесты одновременно не выполнялись.
Время включает четыре durable-вызова с их консолидациями и запись небольших
сводок между фазами. Подготовка проекта, последующая инспекция состояния
и replay в него не входят. Пик RSS относится ко всему процессу стенда,
включая инспекцию и replay.
