# Контракт хранения памяти

Этот документ описывает физическое представление журнала `ProjectMemoryStore`
и компактное представление active frame. Правила поиска, проверки оснований,
допуска действия, консолидации судом остаются у прежних владельцев. Измерения
публикуются отдельно в [MEMORY_PERFORMANCE.md](MEMORY_PERFORMANCE.md).

## Событие, физические байты, receipt

У записи остаются три разные идентичности:

| Объект | Что он связывает |
|---|---|
| Логическое событие | Канонические байты `element-owner-event/v1`: `schema_version`, `kind`, `job_key`, `payload` |
| Физическое представление | Проверяемые блоки дерева, из которых восстанавливаются ровно эти байты |
| Receipt публикации | `transaction_id` плюс `ref` логического события |

`ref` рассчитывается по восстановленным каноническим байтам события. Замена
`event.json` физическим manifest не меняет этот `ref`. SHA-256 блоков означает
совпадение содержимого; он не заменяет receipt публикации, источник наблюдения,
его время, статус или право использования. Разные события могут ссылаться на
одни физические блоки, сохраняя собственные логические записи.

В каталоге транзакции допустим ровно один физический член:

- `event.json` — прежние полные байты события;
- `event-manifest.json` — канонический manifest версии
  `synapse.stage4.gold.memory-event-blocks/v1`, сохранённый прежним writer;
- `event-tree.json` — корень нового дерева версии
  `synapse.stage4.gold.memory-event-tree/v2`.

Новый writer сохраняет небольшие события как `event.json`, крупные — как
`event-tree.json`. Writer плоского manifest v1 в продукте отсутствует;
поддержка этого формата остаётся только при чтении существующей памяти.

В terminal marker поле `members` связывает имя, длину и SHA-256 физического
члена транзакции. Поле `marker_sha256` связывает логическое событие, а
`boundary_id` — его `job_key`. Поэтому совпадение одного физического блока
не позволяет подставить другую логическую публикацию.

## Область общего хранения

Все поддерживаемые `EVENT_KINDS` получают дерево, если полные канонические
байты события занимают **больше 64 KiB**. Это относится к `REQUESTED`,
`STARTED`, `FRAME_COMPLETED`, `OUTCOME_RECORDED`, `CONSOLIDATED`, `OBSERVED`,
`JUDGED`, `MEMORY_BOUND`, `SESSION_OPENED`, `CONSOLIDATION_REPORTED`,
`SNAPSHOT_BOUNDARY`, `MEMORY_RETENTION`, `MEMORY_STATE`, `MEMORY_TRIAL`.
На границе 64 KiB или ниже новое событие сохраняется как `event.json`.

Кодировщик делит точные байты на блоки с максимальным размером 64 KiB. Начиная
с отступа 16 KiB он ищет первую последовательность байтов `},` в пределах
этого блока; при её наличии граница проходит после неё, иначе — на пределе
размера. Последний блок может быть короче 16 KiB. Эта последовательность
служит только выбору границы: кодировщик не трактует её как JSON-объект,
не пересказывает содержимое, не меняет порядок полей. Блок может содержать
лишь часть JSON или UTF-8; декодирование выполняется после полного соединения.

Листья с байтами события и внутренние узлы находятся в
`project-memory/blocks/<sha256>.bin`. Корень `event-tree.json` содержит
`logical_sha256`, `logical_byte_length` и descriptor `root`. Descriptor
содержит `sha256`, `byte_length`, `logical_byte_length`, `height`. Высота 0
обозначает лист: его физическая и логическая длины равны. Внутренний узел
имеет схему `synapse.stage4.gold.memory-event-index/v2` и упорядоченный список
`children` с такими же descriptors.

Корень, каждый внутренний узел и каждый лист занимают не более **64 KiB**.
Узел содержит от **2 до 256** детей; при росте числа листьев добавляются уровни,
а не растёт один неограниченный manifest. Кодировщик распределяет детей между
узлами так, чтобы остаток не создавал одноэлементный узел. Читатель проверяет
точную форму, длину и SHA-256 физических объектов, убывание высоты, суммы
логических длин, отсутствие цикла по предкам. Повторное использование одного
блока в разных ветвях разрешено. Итоговые длина и SHA-256 связывают также
порядок всех восстановленных байтов.

Идентификатор блока — строго 64 строчных шестнадцатеричных символа.
Произвольный путь в descriptor не допускается. Сохраняются прежние требования
канонического кодека и hash-bound references.

Предел **16 MiB на полное логическое событие** и предел **4096 каталогов
транзакций за жизнь журнала** сняты. Дальнейшая запись не требует удаления
истории или замены старых receipts. Для чтения прежних raw/v1 событий
сохраняются их исходные ограничения: 16 MiB логических байтов, до 1024 ссылок
в плоском manifest v1. Эти ограничения старого формата не применяются к v2.

Runtime history, checkpoints и хранилище доказательств Store D этим форматом
не переводятся на блоки.

## Публикация под существующим владельцем

Единственным входом публикации логического события остаётся
`ProjectMemoryStore.put(..., guard=...)`. Нужны текущая owner session,
её живой guard и mutation ticket существующего coordinator. Физический
адаптер не принимает решений о допуске опыта или действий.

Порядок записи следующий:

1. Проверить контракт события, канонизировать его полные байты.
2. Закрепить необходимые записи каталогов до зависимых файлов. На POSIX
   `ensure_durable_directory` синхронизирует сам каталог и его родителя; порядок
   охватывает корень project memory, `events`, `blocks` и каталог новой
   snapshot-транзакции.
3. Сохранить листья, затем внутренние узлы по уровням через существующие
   staged/immutable primitives. Все зависимости закрепляются до корня события.
   Уже существующий блок сначала проверяется по длине и SHA-256.
   Синхронизация самого каталога нужна также при повторном использовании:
   предыдущая попытка могла создать последнее имя блока, затем прерваться
   на ошибке синхронизации. До успешного закрепления каталога manifest
   публиковать нельзя.
4. Сохранить ограниченный корень дерева либо небольшое `event.json` внутри
   новой транзакции.
5. Записать terminal commit marker, после чего событие становится видимым.

Применяется прежний платформенный профиль долговечности persistence.
Успешная запись manifest не заменяет сохранение его блоков. Ошибка публикации
инвалидирует удерживаемый inventory этой owner session; продолжать работу
через прежнее представление после пойманной ошибки нельзя. Восстановление
проверяет видимый журнал перед закрытием брошенного mutation interval.

При физическом чтении транзакции проверяются marker и его члены, descriptor
каждого блока, длина, SHA-256, полная длина и SHA-256 восстановленного события.
Затем действует строгий канонический декодер и прежний контракт события.
До чтения физических членов reader ограничивает их количество одним и
декларируемую длину прежним максимумом 16 MiB, необходимым для raw/v1.
Декодер корня v2 дополнительно проверяет предел 64 KiB. Подделанный marker
не разрешает загрузить произвольное число членов или член произвольной длины.

Кеш разобранных событий по транзакции и digest не отменяет чтение и проверку
их физического представления. Удерживаемый inventory внутри непрерывной
owner session сохраняет прежнее правило повторного использования проверенного
среза; наружу выдаются отдельные копии.

## Совместимость сохранённых данных

Новый читатель понимает прежние `event.json` и плоские manifest v1 рядом
с новыми деревьями v2.
Существующие события автоматически не переписываются и не мигрируют.
Повторная публикация того же события возвращает исходный receipt после
проверки его сохранённых байтов. Старые цепочки, срезы и replay продолжают
ссылаться на свои логические записи.

Новый читатель обратно совместим со старыми записями. Версии Synapse до
поддержки v2 не умеют читать `event-tree.json`; более ранние версии также
не понимают плоский manifest v1 или компактный active frame. Откат программы
к несовместимой версии после новых записей не является поддерживаемым чтением
этого журнала. Автоматического преобразования деревьев обратно в старые формы
нет.

Совместимость записей не отменяет закрепление исполняемых исходников Gold.
Если `runtime_sha256` ранее замороженного эксперимента отличается от текущего,
его выполнение или возобновление по-прежнему отклоняется. Подтверждённый
replay сохранённого durable-корпуса памяти не означает разрешения исполнять
старый Gold-эксперимент под произвольно изменённой программой.

## Сбор осиротевших блоков

GC доступен доверенному владельцу через существующую owner session:

```python
from pathlib import Path

from synapse.experiments.gold.project_memory_store import ProjectMemoryStore

store = ProjectMemoryStore(Path(project_state_root))
with store.session() as guard:
    result = store.collect_unreferenced_blocks(guard=guard)
```

`project_state_root` здесь — уже известный владельцу корень состояния проекта.
Это Python API обслуживания, не команда DSL и не дополнительный инструмент
worker. Read-only store или завершённый guard не разрешают сборку. Результат
содержит `removed_blocks`, `removed_staged_files`, `removed_bytes`,
`retained_blocks`.

Перед первым удалением проверяется весь inventory, включая конфликты
логических событий. Затем проверяются физические корни всех committed-событий,
их внутренние узлы, листья и пространство имён блоков. Отсутствующий terminal
marker означает незавершённую подготовку; существующий повреждённый marker,
каталог вместо него или symlink блокирует удаление. Неизвестная запись,
symlink либо файл неподходящего типа в каталоге блоков также блокирует GC.

Корнями являются **все исторические committed-события**, включая старые
снимки и записи о впоследствии забытом опыте. После проверки удаляются только
неиспользуемые листья, внутренние узлы и оставшиеся staged-файлы блоков.
Удаление выполняется под mutation ticket с синхронизацией каталога на POSIX согласно прежнему
платформенному профилю. Каталоги незавершённых
транзакций этим API не удаляются.

`forget` по-прежнему относится к действующему контракту опыта и его
доказательствам в Store D: владелец записывает акт удаления, сохраняет
надгробия, учитывает основания оставшихся случаев. Общие байты журнала не
расширяют его полномочия. GC не удаляет committed-историю из-за забывания
случая и не восстанавливает право использовать забытое основание.

Автоматического запуска GC нет. После прерывания до terminal marker блоки
могут остаться без committed-корня. Повторные прерывания могут накапливать
такие блоки. Их удаляет явный вызов владельца; обещания автоматического
ограничения этого остатка нет.

## Продолжение журнала coordinator

Счётчик mutation epochs по-прежнему определяется полной сохранённой историей
координатора. Её кадры проверяются последовательно: сохраняются контрольные
суммы, границы кадров, чётность открытого интервала и возможность прочитать
старый recovery payload. Предел числа кадров и совокупного размера именно
этого журнала снят. Ограничение размера отдельного кадра сохраняется.

Этот путь не обрезает журнал, не меняет нумерацию epochs и не подменяет историю
сохранённым счётчиком. Повреждённый или оборванный кадр по-прежнему блокирует
работу до предусмотренного восстановления. Проверка памяти предшествует
закрытию брошенного интервала.

## Компактное представление active frame

Новый `REQUESTED` закрепляет `frame_storage` со значением
`synapse.stage4.gold.compact-active-memory-frame/v1`. По этому полю формируется
`FRAME_COMPLETED`. Повтор и восстановление используют исходный запрос.
Отсутствие поля у старого запроса сохраняет прежнее развёрнутое представление,
включая незавершённые задания. Неизвестная версия отвергается.

Компактная форма содержит метаданные frame, метаданные каждого элемента,
локальную таблицу `values` и целочисленные ссылки из состояний элемента и его
восьми видов памяти. Равные канонические значения сохраняются в таблице один
раз; каждое логическое вхождение остаётся привязанным к своему элементу.
Сохраняются `expanded_bytes` и SHA-256 полного развёрнутого frame.

Кодек принимает исходные frame v1/v2/v3/v4. Число элементов ограничено прежним
`MAX_MODEL_ELEMENTS`. Перед созданием развёрнутых копий проверяются форма,
границы ссылок, отсутствие неиспользуемых значений и точный вычисленный размер.
Бюджет рассчитывается по целому развёрнутому `FRAME_COMPLETED` с его моделью,
owners, ссылками и envelope; упаковка не даёт обойти прежний предел **16 MiB**.
Он теперь явно принадлежит публикации frame (`MAX_FRAME_PUBLICATION_BYTES`),
а не общему хранилищу событий. Предел публикации owner registry **8 MiB**
также сохраняется отдельно. Возможность хранить более крупную историю не
расширяет срез памяти, выдаваемый worker.

`read_active_memory` сначала проверяет связку `REQUESTED` → `STARTED` →
`FRAME_COMPLETED`, исходный source snapshot, selection и закреплённый срез
суда. Из этих оснований повторно строится ожидаемый payload, который должен
полностью совпасть с сохранённым. Только после этого раскрываются локальные
ссылки и проверяется идентичность развёрнутого frame.

Таблица не содержит механизма чтения произвольных receipt, файлов или соседних
записей. Отрицательный индекс, `bool`, строка-путь, внешний descriptor или
индекс за пределами таблицы отвергаются. Каждое восстановленное вхождение
получает собственную копию: изменение одного элемента не меняет другой
элемент либо сохранённую таблицу. Worker получает прежнее развёрнутое
представление через `_memory_information`; формат ссылок ему не передаётся.

Упаковка frame — отдельная версия содержимого новых заданий. В отличие от
физического разбиения события на блоки, она меняет сохраняемый payload нового
`FRAME_COMPLETED`; это изменение закреплено в его `REQUESTED`. Равенство
worker-представления не означает равенство receipt старого и нового задания.

## Оставшиеся ограничения масштабирования

Ограниченные физические объекты не означают ограниченную RAM всего процесса.
Writer канонизирует целое событие; reader соединяет его листья, затем
декодирует весь результат. Кеш и owner session удерживают разобранные события,
inventory проверяет все сохранённые события даже при выборе одного `kind`.
Снимки состояния и boundary по-прежнему содержат полные логические структуры.

Чтение epoch выполняет линейный обход сохранённых кадров. Последовательная
проверка не держит весь epoch journal в RAM, но не устраняет стоимость его
обхода. Размер диска, RAM, стоимость декодирования, копирования и консолидации
остаются практическими ограничениями. Этот патч снимает фиксированные отказы
роста хранения; он не доказывает неограниченный объём памяти, постоянное время
открытия или масштаб миллионов семантических версий.

## Приёмочные границы

Поведенческие проверки находятся вне продуктового кода, в
`acceptance/stage4/stage16/`:

- `test_project_memory_shared_event_contract.py` — точные логические байты,
  разные публикации при общих блоках, смешанный raw/v1/v2 журнал, отдельные копии.
- `test_project_memory_shared_event_corruption.py` — повреждённые, отсутствующие
  или подменённые symlink листья и узлы; неверные корни при корректном
  физическом marker; перестановка детей с пересчитанным хешем узла;
  строгий разбор старых событий; подмена логической публикации.
- `test_project_memory_shared_event_recovery.py` — прерывания публикации,
  восстановление, GC только осиротевших блоков, отказ до удаления при
  повреждённом inventory, права владельца, отказ синхронизации каталога.
- `test_compact_frame_contract.py` — точное восстановление v1/v2/v3,
  неизменная выдача worker, независимые копии, границы ссылок, происхождение,
  предел развёрнутого размера.
- `test_compact_frame_publication_acceptance.py` — настоящий путь публикации,
  retry старых форматов, отказ самосогласованной подмены соседними данными до
  выдачи worker.
- `test_compact_frame_scale_acceptance.py` — отдельный тяжёлый сценарий
  представления frame с полной проверкой выдачи worker.
- `test_project_memory_large_event_growth_acceptance.py` — отдельные тяжёлые
  случаи для всех `EVENT_KINDS` за прежним пределом 16 MiB: многоуровневое
  дерево, повторное открытие, точные receipts, сохранение после GC.
- `test_project_memory_journal_growth_acceptance.py` — продолжение реальных
  публикаций за прежней границей 4096 событий с проверкой старых записей.
- `test_memory_coordinator_growth_acceptance.py` — продолжение owner work после
  сохранённого журнала более миллиона кадров, восстановление незакрытого
  интервала, сохранность старой истории и recovery payload.
- `test_memory_physical_member_bounds_acceptance.py` — отказ по количеству
  и размеру физических членов до чтения их файлов.
- `test_memory_coordinator_validation_acceptance.py` — повреждённые кадры,
  оборванный хвост, старые recovery payload и запрет записи через чужой guard.

Сквозные тяжёлые сценарии находятся в отдельных файлах `acceptance/memory/`:

- `test_storage_growth_acceptance.py` — крупная память через публичный runtime,
  коррекция, отказ действия со старым основанием, перепланирование,
  исторический поиск и replay без повторного внешнего эффекта.
- `test_storage_growth_recovery_acceptance.py` — аварийное завершение процесса
  после решения суда при публикации крупного boundary или state snapshot;
