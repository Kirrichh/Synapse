## Scope and authority

The uploaded **Gold Execution Specification v2.2 NORMATIVE** is the normative
source; **Implementation Patch Plan v1.3** orders delivery. The uploaded
**«Что такое синапс»** describes the wider system. This patch concerns the
existing Stage 11 experiment. It does not claim completion of Stage 4,
StructuredOutcome/FULL verification, publication authority, telemetry
reconciliation, or a demonstrated economic benefit.

The plan's Stage 7 phrase “one snapshot per run” conflicts with specification
§21's immutable snapshot per attempt. The latter governs: changed attempt
inputs require a new snapshot with exact predecessor lineage.

The implementation choices below fill gaps in §26's frozen retry/recovery
policy. They are explicit experimental choices, not claims that external
papers define Synapse's authority rules.

## Frozen experimental decisions

1. `CONTINUE` permits preparation. It does not authorize consumption. Every new
   attempt still needs its own snapshot, retrieval evidence, replay and fresh
   consumption/plan authorization.
2. A first NO_CANDIDATE or infrastructure outcome supplies no independently
   checked hypothesis. Repeating such an attempt requires other new admitted
   evidence; the label alone cannot purchase another model call.
3. Candidate novelty means a different independently evaluated patch/verdict
   pair for the same frozen task/base. This is not a proof of semantic
   inequivalence of arbitrary programs. Attempts remain bounded.
4. Preparation with an uncertain outcome stops. An external action without a
   durable completion is not silently retried. The existing stores remain the
   owners of snapshot and reference-capture history; the new checkpoint does
   not duplicate those schemas.
5. Admission time includes elapsed downtime. Clock regression is unavailable,
   not additional budget. Every recorded worker call contributes its full
   reported token total; partial/unknown totals are not zero. A future strict
   provider cap needs a provider/model contract for per-request reservation and
   cancellation; it cannot be inferred from subprocess telemetry.
6. Prior-run facts are bounded operational feedback in the existing intent
   proposal. They do not become reusable library knowledge and do not establish
   publication, compatibility, correctness or execution authority.

  approval policy and technical sandbox boundaries are distinct controls;
  authorization can cover one action or a class of actions for a session.
  The Synapse implementation uses that interaction principle, with exact
  run/plan grants, and does not claim to reproduce Codex's sandbox or service.
- [LangGraph Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api):
  completed tasks can be loaded from checkpoints; unfinished work needs explicit
  retry/idempotency semantics. This informed the preparation uncertainty
  boundary, without adding LangGraph as a dependency.
- [Temporal: idempotency and durable execution](https://temporal.io/blog/idempotency-and-durable-execution):
  durable orchestration alone does not make external effects exactly-once.
  Accordingly, this patch makes no exactly-once claim for provider requests.
- [Reflexion paper](https://arxiv.org/abs/2303.11366):
  feedback can inform a later trial. It does not establish independent
  correctness or permission. Only C1-backed facts are projected here; there is
  no claimed accuracy gain from this patch.
- [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents):
  bounded workflows can fit predictable tasks. The existing constrained plan
  remains in use; no second planner or orchestration framework was introduced.
- [Mini output format](https://mini-swe-agent.com/latest/usage/output_files/):
  trajectories carry model statistics and per-message raw responses. A cost
  total is not a complete token total; call accounting must cover the history.
- [SWE-bench evaluation guide](https://www.swebench.com/SWE-bench/guides/evaluation/):
  result caching depends on the evaluation run/instance identity. Inspected
  `gold_oracle_binding.py` generates a UUID-suffixed run id per invocation.
  **A reused-result cache defect was not confirmed**, so the C1/oracle modules
  were not changed on that suspicion.

## Architecture and verification

No numerical LOC acceptance rule is introduced. Existing owners retain their
responsibilities. The new `runner/budgets.py` owner reconciles execution evidence before admitting
another attempt. The new `stage10/approval.py` owner controls the independent
operator-grant lifecycle and its evidence. Neither owns planning, compatibility,
C1 classification or the retry decision.

No production dependency or alternate runtime path was added. No C1 production
module was changed. Heavy new preparation-recovery, worker-budget, clock-regression and operator-approval/resume
scenarios have separate files and separate GitHub Actions matrix entries. Lightweight
policy/parser checks extend their existing suites.

must not be added together as a unique test count.

The approval integration test issues the real canonical CLI command, executes

and resumes the terminal result without another worker/oracle call. The worker
is a real fixture subprocess; the oracle outcomes are scripted. These are
acceptance results, not a live provider experiment or evidence of savings.

## Operator approval: one command, bounded automatic continuation

Configure the existing `GoldAttemptPlanProfile.approval_policy` with a
`RunApprovalPolicy` naming the exact frozen manifest hash, governing human and
an absolute operator-owned store outside worker repositories. The policy makes
the profile's capability require operator approval; it does not change its
allowed operations or widen its scope.

Before preparing an attempt, the existing controller checks that policy. When
no matching live grant exists it raises `ApprovalRequired` with the generated
request path. The manifest and completed prior attempts remain durable, but no
preparation-start record, snapshot, replay or model call is made for the paused
attempt. The operator can inspect the request and issue:

```bash
python -m synapse approve /operator/approvals/requests/REQUEST_SHA256.json --store /operator/approvals --for-seconds 3600
```

Calling the same composition's `execute()` then resumes. No second controller
or approval runtime is introduced. The grant covers repeated exact conditions
in this run; only attempt-local snapshot/proposal identities and typed data-only
feedback may differ. Actual compatibility still has to be established for each
attempt. The declaration used for the approval request and actual proposals is
constructed by the same plan owner.

The command prints the grant reference. Revoke it with:

```bash
python -m synapse revoke-approval GRANT_SHA256 --store /operator/approvals
```

Receipts prove the grant was valid at review time. Historical decision decoding
uses that recorded time. New decisions and the existing first-side-effect
barrier check the live grant again, including expiry and revocation. Revocation
does not retract an external action already started. Duration defaults to one
hour and is explicitly bounded to 1 second–7 days; this is an experimental
policy choice, not a normative community limit.

The configured store is the local operator trust boundary. Requests do not
grant authority. Store files are private and append-only; no secret or authority
store path is sent in worker context. This is not OS isolation from an
adversarial process running with the operator's own filesystem permissions;
deployments needing that separation must protect the store with their process
or container identity boundary. No claim is made that these local CLI controls
implement Codex's internal approval service or its security boundary.

The approval CLI is wired through the existing Stage 10 composition root into
`python -m synapse`. This does **not** resolve the separate missing production
Gold run/seed assembly described below.

Wire contracts changed explicitly: intent v2, worker-delivery body v2, attempt
result v3 and continuation evidence v4. No aliases silently reinterpret older
bytes under the new rules. Archived runs must remain paired with their frozen
implementation/version set; this patch is not a migration of historical runs.

## Remaining completion work

The next production increment must define a **frozen experimental input
contract**, then assemble the existing owners from it through `synapse.cli`:
task/base, provider/model, exact oracle/environment, constrained plan, policies,
budgets, and a preverified seed corpus with resolvable evidence and behavior
programs. Reopen the seed as durable input; create isolated run state and
per-attempt snapshots; rehydrate the same bindings on resume. The acceptance
helpers' always-true probes are not a valid implementation of this contract.

That input/assembly contract and the remaining §24 obligations are unresolved
in this correction. Passing the acceptance scenarios below must not be
reported as a production Gold run, FULL verification, Stage 4 completion, or
proof of savings.
